# Prompt engineering for creative AI projects

**Type:** Self-initiated / AI-assisted / Creative R&D
**Section:** creative
**Role:** Prompt engineer, AI collaborator, creative director
**Year:** 2026
**Status:** ongoing

## Summary

A methodology for steering an AI assistant through long creative projects: how to keep the role, the memory and
the working style of the model between sessions. It grew out of the Lorien case and was applied in the D&D
module, Tavern Tales and the emotional layer work (now a section of this case). This is a meta-case: it describes
the approach used by every other creative project.

## Problem

A project that lasts for months is split into dozens of sessions with a model. Every new session loses everything:
the assistant's role, the accumulated agreements, the style, the project terminology, past decisions. Retelling
the context by hand eats time and degrades with repetition. A second problem is controllability: without
formalised rules the model mixes modes (learning, creative work, technical review) and produces an averaged
answer that fits none of the tasks.

## Solution

1. An AI character with a role: the assistant has a name, a purpose and boundaries — it is not "an assistant in
   general" but a specific performer with a defined area of responsibility.
2. Activation codes: short phrases that switch on the required mode without restating the rules.
3. "Memory crystals": context packed into structured blocks that are carried into a new chat as a whole, instead
   of retelling "what we did before".
4. Context versioning: blocks have versions (1.0, 2.0, 3.0 and thematic assemblies), so it is clear what changed
   and which version to attach for a given task.
5. Ritual invocation phrases per mode: separate wording for mentoring, creative work and technical review —
   switching becomes an action, not a request.
6. Memory injection: feeding new facts and project decisions into the assistant's working context.
7. Emotional layer control: tone and depth are configured separately from the content — important both in
   learning and in creative work (details in the section below).
8. Working with an artifact tool (Cline): what was discussed becomes files, tables and documents instead of
   staying in the chat.
9. Carrying the methodology over to technical tasks: the same approach is used in the knowledge base AI pipeline
   (issue → note) and in agent orchestration on the game project.

## Emotional layer control

A separate layer of the work, previously a standalone case: how to build emotional response and personalisation
into stories generated by a model.

1. Personal themes as a source of inspiration: concrete experience sets the plot and details, but enters the text
   reworked — without names, places and circumstances.
2. A character-muse: an image assembled from the qualities of a specific addressee, which links the story to a
   person rather than to an abstract audience.
3. A mandatory hook scene: every story contains an image the reader holds on to — not a plot twist, but a scene
   worth retelling.
4. Feedback changes the tool, not only the text: after a real reader's reaction the assistant assembly was
   reworked to version 3.0.
5. Privacy as part of the design: before any demonstration personal material goes through manual review; there
   are no public examples in this direction — hence the decision not to keep it as a separate case.

## Skills demonstrated

- Prompt engineering: instructions that define behaviour and role, not a one-off answer.
- AI collaboration: organising long-running work with a model over months.
- Memory design: carrying context between sessions through structured blocks.
- Creative direction: tasking the model and holding the project style.
- Context structuring: separating the core, roles, rules and scenarios.
- Carrying the methodology over to technical tasks: CI pipeline, agent rules, orchestration.
- Process documentation: artifacts and templates instead of knowledge kept in one's head.

## Tools

LLM chat models (including DeepSeek), Cline for writing artifacts to files, Markdown, GitHub Actions (in the
technical application of the methodology).

## Limitations

- There is no public documentation of the methodology: everything is private and the template cannot be reused
  out of the box.
- There is no single template either — each project uses its own assembly of blocks.
- Effectiveness was not measured: there is no data on how much time the approach saves.
- Some techniques are tied to a specific project and do not transfer without rewriting.
- The techniques are not packaged as an open-source template for the community.

## Artifacts
